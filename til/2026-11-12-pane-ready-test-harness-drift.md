# 2026-11-12 Today I Learned: pane_ready 테스트 하니스 드리프트로 인한 결정적 실패 4건

## 1. 배경 및 문제 상황

`tests/test_pane_ready.sh`가 로컬과 CI **양쪽에서 결정적으로** `PASS=16 FAIL=4`로 실패했다
(3회 연속 동일 수치, 스위트 44.2초). flake가 아니라 매번 같은 4건이 재현되는 상태였다.

- `ready_미준비후_회복: rc=0` / `ready_프로브_1회성공` (calls 0 != 1)
- `ready_지연_회복: rc=0` / `ready_지연_회복: 프로브 3회` (calls 0 != 3)

당초 "환경 flake" 또는 "제품 재시도 로직 버그"로 의심됐으나, E2E 케이스(실제 `bin/herdr-team` 구동)는
정상 PASS라 제품 배선은 건강했다.

## 2. 원인: 커밋 `e774b35` 이후 하니스 드리프트

- `e774b35`(win-fix)가 제품 `pane_shell_foreground()`의 jq 호출을 `jq -r` → `jq_text`(CRLF 방어 래퍼)로 교체했다.
- 그런데 `tests/test_pane_ready.sh`의 함수 추출 하니스(`extract_fn` + FN_SRC 블록)는
  `log`/`run`/`pane_shell_foreground`/`wait_pane_ready`만 실었고 **`jq_text`를 함께 싣지 않았다**.
- 추출 환경(source 한 FN_SRC)에서 `jq_text: command not found` → `pane_shell_foreground`가 **항상 실패**
  → 게이트 루프가 타임아웃까지 회전. 제품 코드는 무변경이 정답이고, **테스트 하니스만 드리프트**한 사례다.

## 3. 증상

- recovery 2건: `rc=1`, 프로브 호출 `calls=0` (게이트에서 막혀 프로브 루프 진입 자체가 없음)
- 스위트 소요 44.2초 = R-recovery(20s 타임아웃 전액) + R-bounded(20s) + 폐쇄 2건(2s+2s).
  정상이라면 ms 단위로 끝나야 할 recovery가 시간 상한을 전부 태우고 있었다.

## 4. 부수 결함: 폐쇄-b의 vacuous green

폐쇄-b("게이트 통과·프로브 미매칭")는 `rc=1`과 에러 문구만 단언하고 있어, 게이트 루프에서 타임아웃되어
**프로브 루프를 한 번도 실행하지 않은 상태**로도 PASS했다. 즉 드리프트를 잡지 못하는 공허한 통과였다.

## 5. 해결 (테스트 파일 1개)

1. **`jq_text` 추출 추가**: `jq_text()`는 한 줄 함수라 `extract_fn`의 `sed -n "/^$1() {/,/^}/p"` 범위가
   닫히지 않는다 → `sed -n '/^jq_text() {/p' "$BIN"` **단일 행 추출**로 FN_SRC에 추가.
2. **경로 분리 단언(폐쇄-a)**: `calls == 0` — 영구 busy는 게이트 루프만 돌고 프로브를 실행하지 않는다.
3. **경로 분리 단언(폐쇄-b)**: `calls > 0` — 게이트 통과 후 프로브 루프에 진입했음을 봉인(vacuous green 차단).
4. 제품 코드(`bin/herdr-team`)·워크플로 무변경. TB-3(폐쇄 타임아웃 2s→1s)은 수정 후 스위트가 목표 상한
   (≤15초) 안에 들어와 **불필요**로 판정해 미적용.

## 7. 교훈

1. **함수 추출 하니스는 의존 함수를 함께 실어야 한다.** 제품 함수를 `source`로 추출해 쓰는 테스트는
   그 함수가 호출하는 헬퍼(`jq_text` 같은 래퍼)를 함께 넣지 않으면, 제품이 정상이어도 하니스만 깨진다.
2. **제품 코드를 리팩터링할 때 테스트 하니스 의존성을 함께 갱신해야 한다.** `jq -r` → `jq_text` 교체 같은
   "동작 동일" 리팩터링도 추출 기반 테스트에서는 계약 변경이다. 커밋 시 `grep -rn 'extract_fn'`으로
   하니스가 추출하는 함수 목록을 확인하는 습관이 필요하다.
3. **vacuous green을 잡으려면 경로 분리를 단언해야 한다.** 실패 경로 테스트는 "실패했다"가 아니라
   "어느 경로를 지나 실패했는지"(게이트만 vs 게이트+프로브)를 호출 카운터로 단언해야 공허한 통과가 사라진다.
4. **실패가 결정적이면 환경 flake 가설을 접어라.** 3회 동일 수치 + E2E는 통과 + 시간이 타임아웃 전액과
   산술적으로 일치 → "결정적 하니스 드리프트"가 먼저 의심 대상이다.
