## 0. 현행 조사 (사실, read-only 확인)

### 0.1 자동 승인 로직 위치와 동작 (`bin/herdr-watcher`)

| 단계 | 위치 | 동작 |
|---|---|---|
| 감지 | `detect_permission_popup()` :106-129 | `herdr agent read <agent> --source visible` 로 화면을 읽고, **마지막 3줄 이내에 `enter confirm`** 이 있고 그 위 어딘가에 `("Permission required", "Allow once", "Allow always", "Reject")` 중 **하나라도** 있으면 팝업으로 판정. **승인 대상 명령 내용은 전혀 읽지 않는다** |
| 승인 | `handle_permission()` :155-213 → `unblock_agent()` :147 | 팝업 감지 → 쿨다운(`--retry-after`, 기본 10s) → 전송 직전 재확인 → **무조건 Enter 전송** → 사후 확인. Enter 는 팝업 첫 선택지 **"Allow once"** 를 누른다 |
| 키 전송 | `send_keys()` :132-144 | `herdr pane send-keys <pane> <keys>` — 화면 내용과 무관하게 지정된 키 시퀀스를 그대로 주입 |
| 폴링 | `run_watch()` :234-291 | 기본 5초 주기, 모든 모니터 대상 에이전트에 대해 위 로직 반복 |

CLI 옵션(:294-313): `--no-auto-allow`(전면 비활성화 kill-switch), `--approve-keys`(기본 `enter`), `--fallback-keys`(기본 비활성), `--allow-on-blocked`(⚠️ **화면을 읽지 않고** `status==blocked` 만으로 승인하는 레거시 경로, 기본 off), `--max-attempts`(팝업 1건당 최대 2회 전송).

### 0.2 현행 보호장치 (이미 존재하는 것)
- fail-closed: 화면을 못 읽으면 승인하지 않음(:121).
- 쿨다운 + 전송 직전 재확인 + `max-attempts=2`: 반복 발사·flapping 억제(TIL 2026-09-23 사고 재발 방지, `tab` 자동 발화 금지 유지).
- 그러나 **"무엇을 승인하는가"에 대한 검사는 0** — 워처는 명령이 아니라 팝업의 존재만 보고 승인한다.

### 0.3 구조적 사실 (위험 판단의 근거)
1. **콘텐츠 블라인드 승인**: 워처가 보는 것은 화면 하단 푸터 `enter confirm` 과 헤더 문자열뿐. 승인되는 명령이 `ls` 인지 `rm -rf /` 인지 워처는 알 수 없고, 팝업 오버레이 뒤라 화면에 명령 텍스트가 아예 안 보일 수도 있다.
2. **시그니처의 광범위함**: 헤더 매처가 4개 문자열 OR 이고 head 가 "마지막 줄 제외 전체 화면"이라, 트랜스크립트에 "Allow once" 라는 단어가 남아 있고 + 하단에 `enter confirm` 푸터를 가진 **다른 종류의 다이얼로그**(파일 삭제 확인, overwrite 확인, trust 프롬프트 등)가 있으면 그것도 "권한 팝업"으로 오탐되어 Enter 를 받는다.
3. **Enter = 첫 번째 선택지 가정**: "Allow once / Allow always / Reject" 순서와 기본 선택이 첫 항목이라는 것은 opencode TUI 현재 버전 관찰에 기반(TIL 2026-09-23). UI 가 선택지를 기억하거나 순서를 바꾸면 맹목 Enter 는 엉뚱한 옵션을 확정한다.
4. **`--approve-keys "right enter"` = Allow always**: 한 번의 위험 승인이 **영구(durable) allow로 누적**된다(§permission-model-optimization-spec 0.1 V2 문서 사실). 워처는 이 확장이 일어나는 것을 감시·제한하지 않는다.
5. **에피피소드당 시도 한계는 있으나 누적 한계는 없음**: 팝업이 계속 새로 뜨면(에이전트가 위험 명령을 반복 시도하면) 승인 횟수 자체는 무제한 — TIL 2026-09-23 의 30초 5회 발사가 에피피소드 단위 억제로 막긴 하나, "에이전트당 시간당 총 승인 예산" 같은 누적 제한은 없다.
6. AGENTS.md 는 오케스트레이터에게 "파괴적 명령은 자동 승인 금지, 사용자 확인"을 요구하지만, **정작 자동 승인을 수행하는 워처에는 그 어떤 검사도 없다** — 가드레일의 공백.

## 1. 파괴적·비가역 명령 시나리오 분석 (무조건 Allow once 승인 가정)

| 시나리오 | 승인 시 실제 영향 | 가역성 | 워처 관점 비고 |
|---|---|---|---|
| `rm -rf <경로>` | 지정 트리 즉시 삭제. 워크트리·홈 디렉터리 대상이면 프로젝트/사용자 데이터 소멸 | ❌ 비가역 | 팝업만 보고 승인. 화면에 명령이 보여도 워처는 판단 안 함 |
| `git reset --hard` | 커밋 안 된 작업 전량 소멸, 롤백 불가 | ❌ (uncommitted) | 양산 명령처럼 보여 승인 피로 하에 통과되기 쉬움 |
| `git push --force` | 원격 브랜치 history 덮어씀 — 팀원 작업 소멸 | ❌ (팀 피해) | 피해가 타인에게 전이되는 점이 특징 |
| `DROP TABLE` / DB 삭제 | DB 자격증명이 있으면 즉시 데이터 소멸 | ❌ | 클라이언트 도구 확인 프롬프트는 opencode 팝업과 별개 |
| `chmod 777 -R /` 계열 | 권한 전면 개방, 보안 하락. 되돌리려면 원래 모드 알아야 함 | △ (사실상 불가) | "설정 변경"이라 인식되기 쉬워 경각심 낮음 |
| `sudo <cmd>` | 권한 상승 실행. NOPASSWD 환경이면 곧바로 시스템 변경 | ❌ | 워처는 opencode 팝업만 승인; sudo 비밀번호 프롬프트는 미응답이나 NOPASSWD 면 무력 |
| `curl … \| sh` | 원격 코드를 사용자 권한으로 실행 | ❌ | 파이프라인 명령이라 화면 추정조차 어려움 |
| (부수) 삭제/overwrite 확인 다이얼로그, trust 프롬프트 | 팝업 시그니처가 겹치면(§0.3-2) **권한 승인이 아닌데도** Enter 수신 | ❌ | 시그니처 오탐 경로 — 명령 시나리오와 별개의 승인 유입 경로 |
| `--allow-on-blocked` 활성 시 | 화면 확인 없이 Enter 주입 → **어떤 프롬프트에든** 키가 들어감 | ❌ | 현행 기본 off. 이 모드는 사실상 콘텐츠 검증 자체가 불가능 |

공통 결론: **현재 워처는 위 표의 모든 행을 동일하게 승인한다.** 차별화 장치가 하나도 없으며, 유일한 안전판은 에이전트가 애초에 팝업을 띄우지 않는 OpenCode 권한 설정(permission 레이어)뿐이다. 워처 레이어는 이의 마지막 보루인데 내용 무검증이다.

## 3. 권고안 — 최소 변경 우선 (P0/P1/P2)

원칙: 기존 정상 흐름(L0/L1 명령 자동 승인)을 하나도 깨지 않는 선에서 위험 경로부터 막는다. 기본값 변화는 "위험한 경우에만 승인하지 않음" 방향(fail-closed)으로만 둔다.

### P0 — 관측 + 최소 차단 (동일 릴리스에서 즉시 적용)
**원칙(안전 승인 불차단)**: P0 세 항목 모두 "안전한 명령의 자동 승인"은 건드리지 않는다. 차단·비활성화 대상은 파괴 패턴과 콘텐츠 검증이 원천 불가능한 경로뿐이다.

1. **감사 로그(후보 6)**: 모든 전송/보류를 JSONL 에 기록(화면 tail 포함). 동작 변화 0, 인시던트 추적 기반.
2. **denylist fail-closed(후보 1+4)**: 화면 텍스트에 파괴 패턴이 보이면 **키 전송 생략 + `[HOLD]` 로그**. 오탐 시 파이프라인이 잠시 정지해 사람이 눈으로 확인 — 피해 방향이 "정지"로 일원화된다. 패턴 목록은 `--deny-patterns` 플래그로 덮어쓰기 가능. ⚠️ **보조선 전제**: 명령 텍스트가 오버레이에 가려지면 발동 불가(§5-A) — 검증 전까지 2차 방어선이며 1차 방어는 OpenCode permission 레이어다.
3. **`--allow-on-blocked` 게이트**: `--allow-on-blocked` + 자동 승인(기본 on) 조합은 **기동 거부** — 이 경로는 화면을 읽지 않으므로 콘텐츠 검증·denylist 어느 것도 적용될 수 없다(§1 마지막 행). 모니터링 전용(`--allow-on-blocked --no-auto-allow`)은 허용. 기존 케이스 g 가 이 조합의 승인을 기대하므로 테스트 수정이 태스크에 포함된다(§4 T3).

근거: §1 의 모든 시나리오에서 "승인 자체는 맨 마지막 관문"이며, 그 관문에 내용 검증 1회·기록·검증 불가 경로의 차단이 생기는 것만으로 비가역 피해의 상당수가 보류로 전환된다.

### P1 — 정합성·계층화 (P0 안착 후)
4. **승인 옵션 정합성(후보 5)**: `right`(Allow always) 포함 키 시퀀스는 `--i-know-allow-always` 전용 플래그 없으면 기각; 헤더 매처를 `"Permission required"` 로 한정해 이종 다이얼로그 오탐 축소. 기존 케이스 f 가 right enter 전송을 기대하므로 테스트 수정이 태스크에 포함된다(§4 T4).
5. **3단계 위험도(후보 3)**: denylist 를 L0/L1(자동)/L2(보류→사람) 계층으로 일반화. `sudo`, `curl|sh` 등 상승·원격실행 계열을 L2 로 편입.
6. **승인 예산(후보 7②) — L2 한정**: 상한 초과 시 **L2(위험) 계층의 전송만** 보류+경고. L0/L1 안전 승인은 예산과 무관하므로 정상 파이프라인이 예산으로 정지할 일이 없다(안전 승인 불차단 원칙 준수). 에피피소드 억제(`max-attempts`)로 못 막는 L2 런어웨이 누적을 완화한다.
   - **전제(프로세스 로컬)**: 카운터는 워처 프로세스 메모리 상태다. 워처 재시작·새 프로세스 기동으로 초기화되므로 **재시작으로 우회 가능** — 이를 숨기지 않고 명세에 남긴다. 예산의 성격은 보안 통제가 아니라 **런어웨이 댐퍼**다(TIL 2026-09-23 유형의 반복 발사 완화).
   - **우회 한계 상향이 필요해지면**: 감사 로그(P0-1)를 외부에서 집계하는 영구 카운터로 승격(P2 검토). 워처 단독으로는 해결 불가라는 한계를 전제로 한다.
   - 기존 스위트 영향: 예산이 **전송 전반**에 적용되고 카운터가 프로세스 경계를 넘어 유지되면, 기존 스위트의 전송 총 9회(b=1, c=1, d=2, f=1, g=1, i=1, j=1, k=1)가 기본 상한(10)에 근접해 케이스 실패가 발생한다 — L2 한정 스코핑이 필수 계약이다(§4 T6).

### P2 — 구조 개선 (필요 근거가 쌓인 후)
7. **settle 요건(후보 7①)**: 팝업 2폴링 연속 지속 시에만 승인(레이스·깜빡임 잔여 제거, 승인 1폴링 지연 감수).
8. **allowlist 트랙(후보 2) + 예산 외부 집계**: 감사 로그 데이터로 안전 명령 빈도가 확인된 뒤, "화면 명령 추출이 신뢰성 있게 가능한지"(§5-A 검증 결과)가 전제되면 도입 검토. 예산의 영구 카운터 승격도 여기서 함께 판정. OpenCode permission 레이어(기존 명세)와 역할 중복 방지를 먼저 정리.

## 5. 검증 전제 (미검증 리스크의 승격) — 리뷰어 반송 사유 4 반영

### 5-A. 팝업 오버레이에서 명령 텍스트 가시성 — **미검증, denylist 의 전제 조건**
- **리스크**: denylist(T2)와 L2 계층화(T5)는 "화면에 보이는 텍스트"에서만 검출할 수 있다. 권한 팝업 오버레이가 명령 문자열을 가리면 가드레일이 발동할 근거 자체가 없다(§1 각주). 현재 이 가시성은 **확인된 바 없다** — 추측으로 "보인다"고 가정해서는 안 된다.
- **검증 방법**(worker 가 측정 작업으로 수행, 코드 수정 아님): 실제 opencode 세션에서 bash 권한 팝업을 띄운 상태로 `herdr agent read <agent> --source visible` 원문을 `tmp_path` 에 캡처 → 명령 문자열 포함 여부를 판정 기록으로 남긴다. 판정 기준: (i) 항상 보임 / (ii) 명령·팝업 유형에 따라 일부만 보임 / (iii) 거의 안 보임.
- **전제 선언(명세 확정 문구)**: **검증이 완료될 때까지 denylist(T2)와 L2 보류(T5)는 2차 방어선(보조선)이다. 1차 방어는 OpenCode permission 레이어(narrow allowlist·기본 ask·policies)이며, 본 명세의 워처 가드레일은 이를 대체하지 않고 누구나 뚫을 수 있는 "마지막 관문의 무검증 승인"을 좁히는 보조 장치다.** 검증 결과가 (ii)/(iii) 이면 T2·T5 발동 조건에 "명령 텍스트가 화면에 노출된 경우에만" 한정을 유지하고, allowlist 트랙(P2-8)은 전제 불충족으로 기각된다.

### 5-B. 열린 질문 (잔여)
- **오탐 시 파이프라인 정지 체감**: HOLD 가 잦으면 병목 재발. 감사 로그로 오탐률을 먼저 측정하고 패턴을 조정하는 운영 루프가 전제. → HOLD 알림 채널(orchestrator read 만으로 충분한지, herdr 알림 기능 연계 필요성) 미확정.
- **팝업 선택지 순서 변경**: opencode 업데이트로 기본 선택이 바뀌면 맹목 Enter 의 승인 의미가 변함. settle 요건과 무관한 구조적 리스크로, 감사 로그의 화면 스냅샷이 변경 탐지의 재료가 됨.
- **감사 로그 개인정보/비밀값**: 화면 tail 에 환경변수·토큰이 찍힐 수 있음. 로그 저장 위치(프로젝트 내 vs 중앙)와 마스킹 여부 미확정.
